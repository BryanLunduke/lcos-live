# LCOS 0.9.1: AMD normal boot lands at a login prompt (#115, #118)

Fix in lcos-base **0.9.1-2** (2026-10-09 CT). Not baked, not published.

## Cause
lcos-base 0.9-1 shipped `/usr/share/X11/xorg.conf.d/05-lcos-amdgpu-modesetting.conf`
(+ `15-lcos-amdgpu-hotplug.conf`). `MatchDriver "amdgpu"` matched **every** GPU on
the amdgpu kernel driver, and LLK has `DRM_AMDGPU_SI=y`, `DRM_AMDGPU_CIK=y` and no
radeon, so SI/CIK/VI/Polaris parts (#118: A8-6410, R5, CHIP_MULLINS 0x1002:0x9851)
were moved off the amdgpu DDX that 0.8 used. The X stack is otherwise identical:
lcos-live-08-04 and 09-04 `filesystem.packages` list the same xserver-xlibre-*
set (core 25.1.9, video-amdgpu 25.1.2, video-ati 25.0.1, fbdev/vesa/nouveau/vmware).
In 0.8 no LCOS snippet existed, so the stock `10-amdgpu.conf` OutputClass put
amdgpu-kernel devices on the amdgpu DDX (xserver-xlibre-video-amdgpu).
`nomodeset` stops amdgpu from binding, so X runs modesetting on simpledrm and works.

## Fix
- Snippets moved **byte-identical** to `/usr/share/lcos/xorg/` (Xorg does not read it).
- `/etc/init.d/lcos-amdgpu-ddx` (rcS, `Required-Start: mountkernfs $local_fs udev`,
  `Should-Start: kmod`; S14 after udev S04, kmod S11 and mountall S12, so it always runs
  before lightdm in rc2) runs `/usr/lib/lcos/lcos-amdgpu-ddx` on every boot.
- Helper: scans `/sys/bus/pci/devices/*` for class 0x03xxxx, vendor 0x1002, reads the
  bound driver. It copies both snippets into `/usr/share/X11/xorg.conf.d/` (05- must sort
  before stock 10-amdgpu.conf) only when there is at least one amdgpu-bound device and
  **every** amdgpu-bound device is Vega/GFX9+. Otherwise it removes them, which gives 0.8
  behaviour exactly.
- Vega+ = amdgpu-bound and NOT in `/usr/share/lcos/xorg/amdgpu-pre-vega.ids`: 204 IDs
  with CHIP_TAHITI..CHIP_VEGAM, generated by `packaging/tools/gen-amdgpu-pre-vega-ids.py`
  from Linux 7.2.6 (`linux-7.2.6.tar.xz` sha256 039aef84...0f606) `amdgpu_drv.c` pciidlist
  and `include/drm/amd_asic_type.h`. The list is closed (no new pre-GFX9 chips), so
  unknown and future IDs count as Vega+.
- Hybrid: OutputClass MatchDriver applies to all amdgpu devices together, so if ANY
  amdgpu device is pre-Vega nothing is installed. Intel+Polaris gives Xorg default;
  Intel+RDNA gives modesetting on the AMD GPU; Kaveri+RDNA gives Xorg default (booting
  wins over the Vega+ GL-modifier fix). Non-amdgpu devices never match the snippet.
- Override: kernel cmdline `lcos.amdgpu=modesetting|amdgpu|auto` (wins) or
  first word of `/etc/lcos/amdgpu-ddx`. Unknown values fall back to auto.
- Waits up to 5 s only while an AMD display device is unbound AND the amdgpu module is not
  yet `live` (skipped with nomodeset/amdgpu.modeset=0). Normal boot costs about 15 ms.
  Result goes to stdout, `/run/lcos-amdgpu-ddx` and syslog. It never runs X and always
  exits 0.
- Packaging: postinst runs `update-rc.d lcos-amdgpu-ddx defaults` and runs the helper once,
  but not in a chroot (ischroot must return 1). That covers live-build and the Calamares
  target, where /sys is the host's. The old 0.9-1 files were not conffiles, so dpkg removes
  them on upgrade. postrm remove/purge deletes the boot-created copies; purge also removes
  the rc links.
- Recipe: `config/hooks/normal/8910-lcos-amdgpu-ddx-guard.hook.chroot` strips any stray
  always-on copy from the image and fails the build if the 0.9.1-2 payload is missing.

## Live login hint
live-config 11.0.3 ignores `user-password=live`; the live password is live-config's
built-in `live` (crypt 8Ab05sVQ4LLps), and the user is `lcos` (`username=lcos`). If X fails,
LightDM (exit-on-failure=false by default) leaves the seat down and the user is at the tty1
getty with no hint. New live-config component
`config/includes.chroot/lib/live/config/2020-lcos-live-login-hint` appends to /etc/issue
on live boots only: log in as `lcos` / `live`, or reboot into "LCOS (safe graphics)".
Calamares removes live-config, and installs copy /etc/issue from the squashfs, so
installed systems are unchanged.

## Plymouth/LightDM ordering
Judged not the cause; this is consistent with a DDX failure. No reporter has supplied
Xorg.0.log or lightdm.log yet (the triage has none), so this is reasoning, not proof:
- `nomodeset` does not take Plymouth off DRM. Plymouth then runs on simpledrm (a DRM
  device, DRM master) and LightDM hands over in the same way (`plymouth deactivate`, then
  X, then `quit --retain-splash`). With the same 0.9 ordering, that path works. The one
  thing nomodeset removes is amdgpu binding, and so the LCOS snippet matching.
- The 0.9 ordering does not depend on the GPU. lcos-live-09-04 boots normally (KMS, splash)
  to the desktop in QEMU under it (lcos-qemu-09-04 serial: modesetting on /dev/dri/card0).
  The reports cluster on pre-Vega AMD, and #118 says 0.8 worked.
- 0.8 and 0.9 X stacks are identical, so the only AMD-specific userspace change is the
  snippet.
Reporter A/B (move the two snippets aside, then `service lightdm restart`) would confirm it.
If logs show Plymouth holding DRM master, revisit the ordering.
